# 실제 저장소 조회 성능 — 2026-09-29

결론: **현재 색인 규모에서는 SQLite를 유지한다.** 경로·영향도 조회는 2초 p95 목표를 충족했다. 전용 DB의 우월성이나 전체 P2 성능을 검증한 결과는 아니다.

추가 근거: [대형 합성 HTTP 검사 버전2](graph-large-performance-2026-09-29.md)는 독립 정답·실패 조건을 보강하고5만노드/20만관계를 새 서버에서3회 측정했다. 이 문서의 소형 실제 저장소 측정과는 별도 데이터/방법이다.

## 측정 대상

- 운영 SMSR 색인 리비전35: 557파일, 1,215노드, 707관계. 색인 시각 2026-09-29 04:19:59 KST.
- 앱: `artifacts/live-p2-python-control/SMSR.App.exe`, 127.0.0.1:49783. 앱 SHA-256: `1E5710BAD7EE749D307561DD45A12CFC9CD2A409B16BE481C11AD6C75542543C`.
- Windows, Intel Core i5-12400F, 논리12프로세서, 물리 메모리17,026,113,536바이트. 운영 DB 파일30,752,768바이트는 **다른 프로젝트·작업 이력까지 포함**하며 해당 그래프만의 크기나 DB 증가량이 아니다.
- 현재 작업 트리와 색인은 다르다. 측정 당시 freshness는 추가16·변경4·삭제0으로 stale이었다. 이번 측정은 저장된 리비전35의 조회만 평가하며 재색인·앱 교체는 하지 않았다.
- 누락 끝점0, 자기 참조0, 중복 참조0. 기존 문서의 미해결 파일 참조2건은 남아 있다. 성능 통과가 이 참조들의 정확성을 보증하지 않는다.

## 방법과 정답 검사

1. SQLite `mode=ro` 트랜잭션에서 해당 리비전의 노드·관계를 읽고 연결을 즉시 닫는다. 전체 운영 DB를 복사하거나 수정하지 않는다.
2. 앱 구현을 호출하지 않는 독립 BFS로 최단 거리와 역방향 도달 집합을 계산한다. 재현 가능한 seed29로 표본을 선택한다.
3. 경로40쌍: 도달32·도달 불가8. 최단 거리 분포는 1단계20, 2단계2, 3단계4, 4단계3, 5단계2, 6단계1이다. 영향도40노드는 유입 관계가 많은 상위20과 나머지에서 무작위20을 사용한다.
4. 동일 연결에서 순차 GET을 보내며 각 유형 예열5회 후40회를 측정한다. 요청 시작부터 응답 본문 수신까지 포함하고 JSON 해석·정답 검사는 시간에서 제외한다. 최대 깊이8, 기존 API 노드 제한은 경로1,000·영향도100이다.
5. 모든 응답의 리비전, 경로 연결·실제 간선·최단 길이·도달 여부, 영향 집합·중복·잘림 표시를 검사한다. 이번 표본에는 잘린 응답이 없었다. 시작/종료 health의 info도 일치해야 한다.
6. p95는 오름차순 `ceil(40×0.95)`번째, 즉38번째 값이다. 쿼리 실패·정답 불일치·리비전 변경·p95 목표 초과는 비정상 종료한다. 검증을 없애는 `python -O`는 거부한다.

## 판단과 남은 범위

- 현재 리비전의 조회만으로 전용 그래프 DB를 도입할 이유는 확인되지 않았다. SQLite 원본 유지 결정을 유지한다.
- 기존 합성5만노드·20만간선 시험과 이번 소형 실제 저장소 시험은 **별도 근거**다. 서로의 데이터를 대신하지 않는다.
- 이 정답 도구는 최대2,000노드·10,000관계의 소형 실제 그래프용이다. 이를 넘으면 명시적으로 중단한다. 대규모용 표본 정답 전략은 별도로 준비해야 한다.
- 실제 대형·고밀도 저장소, 동시 사용자/색인, 본문 임베딩·Cypher, 초기 색인 시간·DB 증가량, 브라우저/WPF 렌더링, 냉시작/냉캐시, 장시간 안정성은 이번에 측정하지 않았다.
- 실제 대형 부하에서 목표가 반복 초과되면 먼저 조회 계획·인덱스를 점검하고, 같은 데이터·질의·정답·환경으로 별도 DB와 비교한다. 16언어 정밀 분석·PDG/taint 및 전체 P2 수용은 계속 미완료다.
