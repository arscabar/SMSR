## 관계 설명에서 확인한 문제

### 다른 클래스의 동명 메서드 후보

`GraphVaultSync.cs:12,42`의 `StatusAsync`, `SaveAsync`가 `GraphRoleBatchService.cs`로 연결된 후보 2개가 생성 설명에 들어갔다. 실제 호출은 같은 partial 클래스인 `GraphVaultService`의 메서드다(`GraphVaultService.cs:9,40`). 격리 색인에는 이 helper 파일이 없었다.

모델은 두 후보를 `INFERRED`이며 호출 대상이 확정되지 않았다고 설명했다. 확정 호출을 만들어낸 환각은 아니지만, 명백히 다른 클래스의 후보가 사용자 설명에 노출되는 것은 유용한 관계 설명이 아니다. 확정 관계 6개는 원문 선언·호출과 일치했다. 4파일만으로 발견한 한계를 전체 색인의 동일 오류로 확대 해석하지 않는다.

### namespace 선언이 파일 포함 관계로 바뀜

동기화된 `GraphVaultSync.cs--ad23b3cc5c155a47.md:39`에 다음 관계가 나타났다.

`GraphVaultSync.cs → GraphRoleBatchService.cs · CONTAINS · EXTRACTED · GraphVaultSync.cs:3`

격리 서버의 읽기 전용 그래프 내보내기에서 원래 대상은 파일이 아니라 `SMSR.App.Mvp` namespace 심벌이었다. 이 공유 심벌의 정규 소유 경로가 `GraphRoleBatchService.cs`이다. 원문 3행의 namespace 선언은 맞지만, `GraphVaultProjection.cs:14`부터 모든 교차 경로 관계를 파일 링크로 투영하여 파일이 다른 파일을 포함하는 것처럼 보이게 했다. 이 문제는 LLM 생성 문장과 별개인 노트 관계 표기의 결함이다.

## 근거 위치와 원문 열기 문제

- `GraphVaultNote.cs:25`는 인용의 실제 위치 대신 근거 구간의 시작행을 출력한다. 예를 들어 동기화 노트 19행은 원문 `:1`로 표시되지만 실제 인용은 `GraphVaultSync.cs:40~43`이다. 27개 인용의 시작행을 직접 계산했으며 모두 표시된 근거 시작행과 달랐다. 원문 구간 자체는 유효하므로 “위조된 인용”은 아니다. 화면에는 구간 시작임을 명시하거나 정확한 인용 범위를 표시해야 한다.
- `GraphVaultNote.cs:18`의 원문 링크는 서버 주소가 아니라 고정 `LocalServer.Port`를 사용한다. 격리 서버는 `54815`인데 생성 노트는 `49783`을 향한다. 따라서 이번 노트의 `QualityTest` 원문 링크는 잘못된 서버에 연결된다. 운영 서버가 기본 포트일 때 같은 실패가 난다고 단정하지 않는다.
- 노트는 모든 설명과 긴 인용을 한 줄씩 나열한다. 내부 enum·코드·제한 문장이 반복되어 핵심 역할을 빠르게 파악하기 어렵다. Markdown 파일 저장은 확인했지만 실제 Obsidian 렌더링 품질은 이 검토에서 검증하지 않았다.

## 완료 품질에 도달하기 위한 후속 순서

1. namespace·선언·포함을 실제 파일 의존 관계와 구분하고, 동명 메서드의 소유 클래스가 다른 후보를 역할 설명에서 제외한다.
2. 근거의 실제 인용 행과 현재 서버 원문 링크를 정확히 연결한다.
3. 역할 한두 문장, 주요 동작, 실제 관계, 제한 순서로 요약하고 긴 인용은 별도 근거 영역으로 분리한다.
4. 선택 코드의 실제 helper 근거를 제한된 양으로 함께 제공한다. 확인되지 않은 구현은 계속 미확인으로 남긴다.
5. 재시도 없이 생성되는 비율과 긴 파일·복잡한 실제 관계 품질을 추가 측정한다. 현재 4개 결과로 전체 파일 자동 설명의 신뢰성을 보장하지 않는다.

이 검토는 결함과 품질 한계를 기록한 것이며 기능 코드를 수정하지 않았다. 기능 검사 통과와 무관하게 **현재 결과를 최종 만족 수준이라고 승인하지 않는다.**
