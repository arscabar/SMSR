# SMSR v1.3.0 통합 테스트 보고서

## 대상과 판정 기준

- 대상: 일일 작업 기록, 복잡 작업 자동 그래프 정책, 캘린더 요약, 상태 카드, 자동 업데이트, stdio 서버 자동 복구
- 판정 기준: Release 빌드와 자체 검사, 실제 stdio 초기화·도구 목록, 설치 업그레이드, 설치 UI, 서버 상태가 모두 통과해야 한다.
- 데이터 안전: 기능 검사는 임시 SQLite·임시 설정 경로를 우선 사용하고 기존 사용자 설정과 이력은 삭제하지 않는다.

## 구현 검토

- `record_daily_activity`는 실제 프로젝트 파일 변경 결과만 받으며 계산·검색·질문·읽기 전용 작업은 제외한다.
- 같은 `activityId`를 다시 보내면 새 카드가 생기지 않고 제목·요약·상태·파일·검증·산출물이 갱신된다.
- 일일 작업은 로컬 날짜 경계를 UTC로 변환해 조회하고 프로젝트·워크플로우·전체 이력 삭제 범위에 포함한다.
- 그래프 자동 생성은 실제 파일 변경과 복잡도 신호 두 개 이상을 동시에 요구한다. 사용자의 명시적 그래프 요청은 항상 우선한다.
- 상태 기록 카드는 노드별 최신 이벤트 하나를 사용하고 계획의 작업 제목, 최신 상태, 진행률, 담당자, 재시도와 산출물을 표시한다.
- SSE가 본문을 교체하기 전에 스크롤과 카드 접힘을 저장하고 교체 후 같은 프로젝트·워크플로우 키로 복원한다.
- 업데이트는 GitHub 정식 최신 릴리스의 Setup EXE와 같은 이름의 SHA-256 파일을 모두 요구하고 해시 불일치 파일을 삭제한다.
- 경로는 실행 중인 PC의 설치 위치와 `%LocalAppData%`에서 계산하며 개발 PC 절대 경로를 제품 코드에 저장하지 않는다.

## stdio 실패와 재계획

기존 화면용 `SMSR.App.exe`는 Windows GUI 서브시스템 실행 파일이므로 Codex가 리디렉션한 표준 출력에 MCP 응답을 내보내지 못했다. 다음 세 검사가 같은 결과로 실패한 시점에 반복을 중단했다.

1. PowerShell 파이프를 사용한 설치 EXE stdio 요청
2. 이전 단일 파일 설치에서 별도 DLL을 `dotnet`으로 실행하는 대안
3. `Start-Process` 표준 입출력 리디렉션 검사

화면 앱을 콘솔 앱으로 바꾸면 일반 실행 때 콘솔 창이 노출될 수 있어, 같은 앱호스트를 콘솔 서브시스템으로 변환한 `SMSR.Bridge.exe`를 설치 내부 구성요소로 생성하는 방식으로 계획을 변경했다. 화면 앱과 브리지는 같은 DLL·런타임을 공유하므로 중복 단일 파일 두 개를 넣던 초기 시제품보다 설치 파일 크기도 크게 줄었다. 사용자가 전달받는 배포물은 Setup EXE 하나다.

최종 커밋 설치본에서 서버가 꺼진 상태로 stdio를 재검사하자 서버는 복구됐지만 검사 클라이언트가 종료를 기다렸다. 브리지가 `UseShellExecute=false`로 시작한 장기 실행 GUI 앱이 부모의 표준 출력 파이프 핸들을 상속한 것이 원인이었다. GUI 앱을 숨김 셸 실행으로 시작해 stdio 핸들을 상속하지 않도록 수정하고, 서버가 없는 상태에서 브리지의 응답과 종료를 함께 재검사했다.

설치 자동 재실행을 포함한 무인 업그레이드를 `Start-Process -Wait`로 감싼 검사는 재실행된 자식 앱까지 기다리는 PowerShell 특성 때문에 대기 상태가 유지됐다. 설치 자체와 파일 교체는 완료됐으며, 정확한 설치 경로·프로세스를 확인한 뒤 앱을 다시 시작해 자체 검사와 서버 상태를 별도로 판정했다.

저장소 전체 `dotnet format --verify-no-changes`는 이번 범위 밖의 기존 `AssemblyInfo.cs`, OAuth 검사와 이벤트 저장소 압축 스타일도 보고했다. 자동으로 전체 파일을 재작성하지 않고 이번에 추가한 C# 파일만 포맷·재검사했으며 `git diff --check`까지 통과했다.

## 남은 위험

- 코드 서명이 없어 SmartScreen 신뢰는 다른 PC에서 사용자가 확인해야 한다.
- 별도 단위 테스트 프로젝트가 없고 주요 회귀 검증이 임시 저장소를 사용하는 실행 파일 자체 검사에 집중돼 있다.
- 현재 환경에는 인앱 브라우저 자동 제어 런타임이 없어 실제 클릭 자동화 대신 설치 WPF UI Automation, 실행 서버의 HTML/SSE 계약과 자체 검사를 사용했다.
- 현재 실행 중인 Codex는 시작 시 읽은 MCP 도구·훅 지침을 캐시하므로 설치 후 한 번 완전히 다시 시작해야 도구 10개가 보인다.
