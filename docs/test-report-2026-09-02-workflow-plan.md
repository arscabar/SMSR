# 워크플로우 식별·동적 계획 경계 테스트 보고서

## 대상과 목적

- 기준 커밋: `1ff89972a52325520201b1d31a2e1ae49fcae5c7`
- 대상 기능: 읽기 쉬운 workflow ID, 활성 계획 재정렬·노드 추가, 기존 진행률 보존, 완료 노드·완료 그래프 불변 처리
- 판정 기준: Release 빌드, 자체 검사 4종, stdio MCP 도구 목록, 설치 앱 서버 상태가 모두 통과해야 한다.

## 진행 경과

1. `dotnet build SMSR.slnx -c Release --verbosity:minimal`을 실행했다. 약 3.00초에 경고 0개·오류 0개로 통과했다.
2. `dotnet test SMSR.slnx -c Release --no-build --verbosity:minimal`은 약 0.96초에 종료 코드 0을 반환했다. 별도 단위 테스트 프로젝트가 없으므로 기능 판정에는 자체 검사를 사용한다.
3. 첫 자체 검사에서 config 검사는 통과했고 tracking 검사는 불투명 ID 응답의 한글 JSON 문자열 비교 때문에 실패했다. JSON을 구조적으로 역직렬화해 `workflowId`와 `replacedOpaqueId` 값을 검사하도록 수정했다.
4. 두 번째 tracking 검사에서는 완료 그래프 오류 응답을 같은 방식의 한글 직렬화 문자열로 비교해 실패했다. `error` 필드 값을 읽는 공통 검사로 수정했다.
5. 세 번째 tracking 검사에서는 동적 계획에 `review` 노드를 추가한 뒤 계층 렌더링 기대값을 기존 `하위 작업 1개`로 유지한 테스트 데이터 불일치를 발견했다. 실제 계획의 하위 작업은 `contract`, `review` 두 개다.
6. tracking 수정 확인 후 종합 `--self-test`를 실행했다. 첫 실행은 HTML로 안전하게 인코딩된 구분자 `·`를 원문으로 비교해 기존 UUID 제목 표시를 오판했다.
7. 두 번째 종합 검사에서는 원인 분리를 위해 MCP workflow를 `mcp-wf`로 임시 격리하고 JSON·HTML 판정을 구조화했다. 이후 진단으로 임시 서버 DB가 앞 단계 DB와 원래부터 분리돼 있어 완료 노드 충돌은 없다는 점을 확인했고, 재시작 복원 시나리오와 일치하도록 ID를 `wf-1`로 되돌렸다.
8. 세 번째 종합 검사는 이름 있는 진단 그룹을 추가해 `bridge`, `mcp-payload` 기대값 오류를 확인했다. 임시 로컬 서버는 별도 DB이므로 계획 저장 전 초기 bridge 목록은 비어 있고, 저장 후에만 `wf-1`이 존재하는 것이 정상이다.

## 반복 실패 중단과 변경 계획

tracking 자체 검사가 세 번 연속 실패해 같은 명령의 재시도를 중단했다. 관찰된 세 실패는 제품 기능 오류가 아니라 새 계약에 맞춰 확장된 자체 검사의 판정 방식과 기대값 오류였다.

다음 순서로 검증을 재개한다.

1. 계층 렌더링 기대값을 실제 동적 계획의 하위 노드 수와 일치시킨다.
2. tracking 검사만 실행해 원인 수정 여부를 확인한다.
3. 통과한 경우 Release 빌드부터 자체 검사 4종을 새로 실행한다.
4. 소스 stdio MCP `initialize`·`tools/list`, 설치 앱 자체 검사, `/api/health`를 확인한다.
5. 최종 결과와 남은 위험을 이 문서와 개발 이력에 기록한다.

종합 검사를 세 차례 실행하는 동안 표시·로컬 서버 단계의 테스트 데이터 오류가 이어져 추가 재실행을 중단했다. 초기 bridge 응답은 오류 없는 빈 목록인지 JSON 필드로 판정하고, 저장 후 목록은 `wf-1`을 기대하도록 수정한 뒤 전체 검증을 처음부터 재개한다. 레거시 UUID 표시 검사용 계획도 WPF가 읽는 서버 DB에 명시적으로 준비한다.

### 기능별 확인 결과

- 새 workflow ID가 `yyyyMMdd-HHmmssfff__프로젝트명__작업명` 형식으로 생성된다.
- 존재하지 않는 UUID session ID를 첫 `save_plan`에 전달하면 읽기 쉬운 ID로 교체되고 `replacedOpaqueId`가 `true`다.
- 기존 UUID workflow는 실제 ID를 유지하면서 최상위 작업 제목과 함께 대시보드·WPF 목록에 표시된다.
- 활성 계획 재저장 시 입력 순서가 반영되고 기존 노드의 60% 진행률은 유지되며 새 노드는 `PENDING`이다.
- 계획에서 제거한 노드의 현재 상태와 heartbeat 참조가 정리되고 변경 알림 버전이 증가한다.
- `SUCCESS(100%)` 노드의 재개·정의 변경·하위 작업 추가와 완료 그래프 변경이 거부된다.
- HTTP MCP의 계획 저장·이벤트 기록·목록 조회, SSE 즉시 변경 알림, 활동 JSONL, 대시보드·요약·내보내기가 통과했다.
- 실패 조건을 단일 문자열 비교가 아닌 JSON 필드와 이름 있는 검증 그룹으로 판정하도록 자체 검사를 보강했다.

### stdio MCP와 설치본

- 소스 DLL stdio와 설치된 `SMSR.App.exe --mcp-stdio`가 protocol `2025-11-25`로 초기화됐다.
- 두 환경에서 `record_heartbeat`, `record_event`, `get_plan`, `get_state`, `save_plan`, `generate_summary`, `save_summary`, `list_workflows`, `export_workflow`의 9개 도구가 확인됐다.
- 설치 프로그램 생성과 무인 업그레이드가 종료 코드 0으로 완료됐다.
- 설치본 자체 검사 4종은 각각 종료 코드 0이었다: config 2.89초, tracking 1.01초, OAuth 1.32초, 전체 11.00초.
- 설치된 서버는 `127.0.0.1:49783`에서 `ready`를 반환했고 외부 주소에는 bind하지 않았다.
- Setup SHA-256: `3D9352C32BB9D3C9662207370F2FEC9943B325818E3AC6E31A2B2A84FF09FD03`
- publish·설치 EXE SHA-256: `A6F43FBC1727D0AEB80929634B707C6BD13A1BADA03328905880192F18C69884`

초기 WinExe stdio 검사기는 요청을 모두 쓴 직후 stdin을 닫아 응답을 받지 못했다. 각 응답을 읽은 뒤 다음 요청을 보내고 마지막에 stdin을 닫는 실제 요청·응답 순서로 수정하자 설치 EXE가 정상 응답했다. 단일 파일 배포이므로 publish 폴더에 별도 DLL이 없는 것도 정상이다.

## 남은 위험과 후속 검증

- 별도 단위 테스트 프로젝트가 없어 회귀 검증이 자체 검사에 집중돼 있다. 순수 ID·계획 경계 로직은 향후 단위 테스트 프로젝트로 분리할 수 있다.
- 이번 설치 검증은 현재 Windows 사용자에서 수행했다. 다른 PC·다른 Windows 사용자의 최초 설치와 DPAPI별 설정 생성은 실제 대상 PC에서 한 번 확인해야 한다.
- 자동 검사는 데이터·서버·MCP·생성 HTML 계약을 확인한다. 다양한 DPI와 창 크기에서의 WPF·브라우저 시각 품질은 별도 수동 UI 검증 대상이다.
