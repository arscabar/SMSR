# 작업 그래프 기반 멀티 에이전트 오케스트레이션

## 목표

작업계획서를 실행 가능한 작업 그래프로 변환하고, 사용자가 대시보드에서 다음을 즉시 알 수 있게 한다.

- 현재 활성 에이전트와 담당 작업
- 현재 실행·검증 중인 노드
- 전체 진행률과 선행 작업 관계
- 실패, 재시도, 차단 사유와 사용자에게 필요한 결정

## 공통 원칙

1. 사용자에게 보이는 응답, 파일, 대시보드는 한국어로 작성한다.
2. 명시적으로 제공된 파일과 지정 워크스페이스 안에서 작업한다. 범위를 벗어난 쓰기·삭제·민감 정보 접근은 사용자 확인 후 진행한다.
3. 데이터 모델, 외부 연동, 보안, 대규모 구조 변경처럼 영향이 큰 작업은 구현 전에 짧은 설계와 완료 기준을 제시한다.
4. 기존 코드와 플랫폼 기능을 우선 사용한다. 필요 없는 클래스, 모듈, 의존성, 대시보드 기능은 추가하지 않는다.
5. 같은 원인으로 같은 노드가 3회 실패하면 재시도를 중단하고 `BLOCKED`로 전환한다. 실패 원인, 시도 내역, 필요한 사용자 결정을 보고한다.

## 역할

### 메인 에이전트

- 작업계획서에서 노드, 선행 관계, 완료 기준을 추출한다.
- 의존성이 충족되고 서로 독립적인 노드는 여러 작업 에이전트에게 동시에 할당한다.
- 상태 변경마다 최신 상태와 이벤트 이력을 기록한다.
- 필수 노드가 모두 `SUCCESS`일 때만 전체 작업을 완료한다.

### 작업 에이전트

- 할당된 노드의 구현 또는 조사 작업을 수행한다.
- 시작, 진행, 완료, 실패 시 상태 이벤트를 기록한다.
- 결과에는 변경 파일, 실행 명령, 결과 요약을 남긴다.
- 진행 중에는 주기적으로 heartbeat를 기록한다.

### 검증 에이전트

- 명시된 완료 기준, 테스트, 빌드, 린트 등 실행 가능한 기준으로만 판정한다.
- `PASSED` 또는 `FAILED`와 함께 근거, 오류 위치, 최소 수정 가이드를 기록한다.
- 모호한 "클린 코드" 판정만으로 실패 처리하지 않는다.

### 대시보드 관리 에이전트

- 최신 상태 파일과 이벤트 이력을 읽어 좌측 에이전트 패널, 중앙 그래프, 우측 상세 패널을 갱신한다.
- 상태 변경이 없으면 불필요한 재렌더링을 하지 않는다.

## 상태 모델

### 작업 노드 상태

`PENDING → IN_PROGRESS → VALIDATING → SUCCESS`

검증 실패 시 `FAILED → RETRYING → IN_PROGRESS`로 이동한다. 진행할 수 없으면 `BLOCKED`로 이동한다.

### 에이전트 상태

`IDLE`, `WORKING`, `VALIDATING`, `RETRYING`, `BLOCKED`, `STALE`

- 에이전트는 한 번에 하나의 활성 노드만 맡는다.
- 여러 에이전트는 서로 독립적인 노드를 동시에 수행할 수 있다.
- `last_seen_at`이 정해진 heartbeat 간격의 3배를 넘으면 `STALE`로 표시한다.
- `STALE`은 자동 성공 처리하지 않으며 메인 에이전트가 원인을 확인한다.

### 계층형 그래프 상태

- 하위 작업은 `parent_id`로 상위 그룹 노드를 가리킨다. 그룹 노드는 `has_subgraph`로 내부 순서도 식별자를 가진다.
- 하위 노드 또는 더 깊은 하위 노드 중 하나라도 `IN_PROGRESS`, `VALIDATING`, `RETRYING`이면 모든 상위 그룹 노드를 활성 상태로 표시한다.
- 메인 그래프에는 활성 그룹 노드를 모두 강조한다. 사용자가 그룹 노드로 드릴다운하면 해당 내부 순서도의 활성 노드를 모두 강조한다.
- 여러 내부 그래프가 동시에 활성일 수 있다. 대시보드는 하나의 내부 그래프를 보고 있어도, 메인 그래프로 돌아가면 모든 활성 그룹을 표시한다.

## 상태 저장과 이벤트

두 파일을 사용한다.

- `workflow-state.json`: 대시보드가 읽는 최신 스냅샷
- `events.jsonl`: 상태 변경마다 한 줄씩 추가하는 변경 이력

모든 상태 변경은 최신 스냅샷을 먼저 일관되게 갱신한 뒤, 동일한 내용을 이벤트 이력에 기록한다. 대시보드는 로컬 HTTP 서버와 같은 출처에서 상태 파일을 읽는다. HTML 파일을 직접 열어 파일 시스템을 폴링하지 않는다.

## 대시보드 요구사항

### 좌측: 활성 에이전트

- 에이전트 이름, 역할, 상태, 담당 노드, 작업명, 경과 시간, 재시도 횟수를 표시한다.
- `WORKING`, `VALIDATING`, `RETRYING` 에이전트를 목록 상단에 표시한다.
- 동시에 활성인 모든 에이전트를 강조한다. 한 에이전트를 선택해도 다른 활성 에이전트의 강조를 해제하지 않는다.
- 에이전트를 클릭하면 중앙 그래프에서 담당 노드를 선택하고 화면 중앙으로 이동한다.
- `BLOCKED`, `STALE` 에이전트는 붉은색으로 명확히 표시한다.

### 중앙: 작업 그래프

- 노드는 작업명, `node_id`, 담당 에이전트명, 상태를 표시한다.
- `IN_PROGRESS`, `VALIDATING`, `RETRYING` 노드는 굵은 테두리와 펄스 효과로 강조한다.
- 동시에 활성인 모든 노드와, 활성 하위 노드를 가진 모든 상위 그룹 노드를 강조한다.
- 활성 노드로 이어지는 선행 간선도 강조한다.
- `SUCCESS`는 초록, `PENDING`은 회색, `VALIDATING`은 보라, `FAILED`·`RETRYING`·`BLOCKED`는 붉은 계열로 구분한다.
- 노드 클릭 시 우측 상세 패널을 갱신하고, 좌측의 담당 에이전트도 함께 강조한다.
- 그룹 노드는 내부 순서도로 드릴다운할 수 있고, breadcrumb로 상위 그래프로 돌아갈 수 있다.
- 드릴다운, breadcrumb, 다른 그래프 위치로 이동하면 선택 노드 상태를 초기화한다.
- 그래프 이동 직후 우측 상세 패널, 실행 로그, `내부 순서도 보기` 버튼을 기본 상태로 되돌린다.
- 새 그래프에서 노드를 다시 선택했을 때만 상세와 드릴다운 버튼을 표시한다.
- 큰 그래프에서는 확대·축소·이동과 완료 노드 숨김 필터를 제공한다.

### 우측: 선택 노드 상세

- 목표와 완료 기준
- 담당 에이전트와 상태
- 최근 이벤트와 실행 로그
- 산출물 경로와 검증 결과
- 실패 원인, 재시도 횟수, 다음 조치

### 경고와 진행률

- 노드마다 `required: true | false`를 기록한다. `required: true`인 노드의 완료 비율로 전체 진행률을 계산한다.
- `BLOCKED` 노드가 하나라도 있으면 상단 경고 배너에 사용자 결정 사항을 표시한다.
- 동일 노드의 재시도가 3회 이상이면 붉은 경고를 표시한다.

## 안전 및 렌더링 규칙

- 작업명, 로그, 오류 메시지, 파일 경로는 신뢰하지 않는 입력으로 취급한다.
- 화면 표시에는 `textContent` 또는 동등한 이스케이프 처리를 사용하며, 로그 데이터를 `innerHTML`에 직접 삽입하지 않는다.
- Mermaid 노드 라벨에는 특수문자를 이스케이프하여 렌더링 오류와 스크립트 삽입을 방지한다.
- 외부 CDN을 사용할 경우 버전을 고정한다. 가능하면 검증된 로컬 자산을 사용한다.

## 완료 기준

1. 작업 단계, 담당 에이전트, 상태 전이가 `workflow-state.json`에 일관되게 표시된다.
2. 좌측 에이전트 선택과 중앙 노드 선택이 서로 동기화된다.
3. 실행·검증 중인 노드와 경로가 시각적으로 강조된다.
4. 실패, 재시도, 차단 사유가 상세 패널과 경고 영역에 표시된다.
5. 모든 필수 노드가 `SUCCESS`일 때만 작업이 완료로 표시된다.

## 참조 구현

대시보드의 화면 구성, 상태 강조, 선택 동기화, `workflow-state.json` 폴링 방식은 같은 폴더의 `dashboard-sample.html`을 참조한다. 샘플은 상태 파일이 없을 때도 내장 예시 데이터를 표시하며, HTTP 서버에서 열면 `workflow-state.json`을 2초마다 읽는다.
